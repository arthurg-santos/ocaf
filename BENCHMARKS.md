# OCAF benchmarks

These are real measurements from the reference implementation. No numbers in
this document are estimates or projections. The corpus is synthetic and fully
deterministic, so the size results can be reproduced exactly (timings vary with
the machine and ambient load).

## 1. Environment

| Item | Value |
| --- | --- |
| CPU | Intel Core i7-3610QM, 4 cores / 8 threads, 2.30 GHz base, 3.30 GHz max |
| RAM | 7.6 GiB |
| OS | Fedora Linux 45, kernel 7.3.4-300.fc45.x86_64 |
| Rust | rustc 1.99.1 (2026-10-13), cargo 1.99.1 |
| OCAF | 0.1.0, format 1.0, `--release` (thin LTO, one codegen unit) |
| FLAC / ALAC | ffmpeg 9.0.2, FLAC `-compression_level 12`, ALAC ffmpeg defaults |
| WavPack | 5.9.0 native CLI, `-hh -x4` |
| Corpus | generated by `scripts/generate_corpus.py`, seed `0x0CAF2026` |

The machine was not isolated: it is a normal Fedora desktop session. Each
timing is the best of three runs to reduce scheduler noise. Only sizes and
bit-exactness are deterministic; treat throughput as indicative rather than a
laboratory measurement.

## 2. Corpus

All files use 48 kHz unless noted. They are generated from a fixed seed, with
no external samples.

| File | Duration | Layout | Content |
| --- | ---: | --- | --- |
| `silence16.wav` | 2 s | stereo, 16-bit int | all zeros |
| `noise16.wav` | 3 s | stereo, 16-bit int | uniform white noise |
| `pinknoise16.wav` | 5 s | stereo, 16-bit int | Paul Kellet pink noise |
| `sine16.wav` | 5 s | stereo, 16-bit int | 440 + 554.365 + 880 Hz tones |
| `music16.wav` | 9 s | stereo, 16-bit int | chord progression with plucked partials and stereo detune |
| `sine24_96k.wav` | 3 s | stereo, 24-bit int, 96 kHz | 1 kHz tone |
| `sine32_mono.wav` | 3 s | mono, 32-bit int | 440 Hz tone at full 32-bit precision |
| `surround24_6ch.wav` | 2 s | 6 channels, 24-bit int | one tone per channel |
| `tone_f32.wav` | 3 s | stereo, float32 | 16-bit-derived values (exact multiples of 2^-15) |
| `tone_f64.wav` | 3 s | stereo, float64 | same 16-bit-derived values |
| `sine_f32.wav` | 3 s | stereo, float32 | full-mantissa double→float32 sine |
| `sine_f64.wav` | 3 s | stereo, float64 | full-mantissa double sine |

The two `tone_f*` files model a common workflow: audio originally quantized to
16-bit PCM and converted to float. The two `sine_f*` files are the hard case:
the low mantissa bits are effectively random rounding noise, so they cannot be
predicted as a smooth integer waveform.

## 3. Results

Sizes are KiB of the encoded file. "PCM" is the size of the WAV `data` chunk,
not the whole WAV container. Ratios are PCM / compressed. Speed is PCM MiB/s,
wall-clock, best of three, including process startup and file I/O. External
cells marked **lossy** failed the byte-identical PCM check and are excluded
from all comparisons. `—` means the external encoder is unavailable or rejected
the format.

## 4. What the numbers mean

### Integer audio

- OCAF produced a smaller file than FLAC on all 9 integer/16-bit-derived
  comparisons where FLAC was bit-exact.
- OCAF produced a smaller file than ALAC on the same 9 comparisons.
- WavPack's strongest reproducible mode beat OCAF on synthetic music by about
  0.8% (850.0 vs 857.1 KiB), on pink noise by about 0.8% (822.3 vs 828.6 KiB)
  and, trivially, on digital silence (0.3 vs 0.4 KiB, where both are
  essentially container overhead). It also wins on full-mantissa float32
  (249.5 vs 351.6 KiB). OCAF won on white noise, pure tones, high-resolution
  24-bit, 32-bit mono, multichannel and 16-bit-derived float.
- On high-resolution material the margin is large: 167.2 KiB versus
  431.2 KiB for FLAC and 351.5 KiB for WavPack on `sine24_96k.wav`; 154.8 KiB
  versus 514.6 KiB for FLAC on six channels.
- White noise is incompressible. OCAF is 563.0 KiB for 562.5 KiB of PCM, a
  0.09% expansion caused by container and frame headers. FLAC is 579.7 KiB and
  WavPack 573.8 KiB on the same file; ALAC is 563.5 KiB. This is the expected
  behavior of a lossless codec on random data.

### Floating-point audio

- `tone_f32`/`tone_f64`, which contain only 16-bit-derived values, compress very
  well: 73.1 KiB from 1125.0/2250.0 KiB. OCAF's exact fixed-point
  representation recognizes that every value is a multiple of 2^-15.
- Full-mantissa float32 is the weak case. OCAF reaches 351.6 KiB; WavPack's
  best extra mode reaches 249.5 KiB. FLAC and ALAC are lossy for full-mantissa
  float input in this ffmpeg build and are not comparable. The 16-bit-derived
  `tone_f32`/`tone_f64` files survive the integer conversion exactly, which is
  why those rows have valid FLAC and ALAC sizes.
- Full-mantissa float64 is the weakest case: 1312.8 KiB from 2250.0 KiB
  (1.71×). No external codec in this environment encoded float64 losslessly
  and accepted the file, so there is no valid external comparison.
- These are honest limits of the current design, not bugs: every float bit is
  preserved, but the predictor sees mantissa rounding noise.

### Why the external table has gaps

The benchmark records a result only if the decoder returns byte-identical PCM.
That check removes several plausible-looking comparisons:

- The ffmpeg FLAC encoder in this build stores 32-bit integer input at 24 bits
  per sample (`bits_per_raw_sample=24`), so `sine32_mono.wav` is not
  bit-exact. FLAC as a format supports higher bit depths in other tools.
- The ffmpeg ALAC encoder is likewise not bit-exact for the 32-bit integer
  file in this build.
- FLAC and ALAC are integer codecs; ffmpeg converts float input to integer.
  Full-mantissa float comparisons are therefore lossy. The 16-bit-derived
  `tone_f32`/`tone_f64` values are exactly representable as 16-bit integers,
  so those conversions are bit-exact and are reported.
- WavPack 5.9.0 accepts float32 losslessly in native mode but rejects float64.
- ffmpeg's native WavPack wrapper was not used for the table when the native
  CLI was available. The native CLI offers stronger and more controllable
  settings.

The `ocaf verify` command performs the same kind of end-to-end check for OCAF:
it decodes every frame, verifies the frame and PCM CRCs, and compares the
resulting PCM against the declared stream CRC.

## 5. Reproduce

```sh
# Build the release binary
cargo build --release

# Generate the fixed corpus (skips existing files unless --force)
python3 scripts/generate_corpus.py
python3 scripts/generate_corpus.py --force   # regenerate deterministically

# Run the full comparison (needs ffmpeg for FLAC/ALAC;
# native wavpack/wvunpack enable the WavPack column)
python3 scripts/benchmark.py --iterations 3

# OCAF-only quick check for one file
target/release/ocaf benchmark testdata/generated/music16.wav --iterations 5
```

`scripts/benchmark.py` also writes `testdata/bench/benchmark.json`, which
contains exact byte counts, timings, encoder methods and bit-exactness flags.
The script never reports a lossy result as a comparison: the `lossy`/`n/a`
markers come from actually decoding and comparing the PCM bytes.

To run without external codecs:

```sh
python3 scripts/benchmark.py --iterations 3 --no-external
```

## 6. Caveats

- The corpus is synthetic. It is designed to exercise specific codec paths
  (silence, noise, tones, transients, multichannel, float rounding), not to
  predict performance on a particular music library.
- WavPack's `-x` modes are not monotonic on all material. `-x4` was chosen
  because it is deterministic and was the strongest reproducible setting on
  this corpus; `-x6` was slower and, on some float files, produced larger
  output. The method is recorded in the JSON.
- FLAC and ALAC were exercised through ffmpeg 9.0.2. Their native command-line
  tools and other builds may support different bit depths and settings. The
  table is a comparison against this environment, not a claim about every
  FLAC/ALAC encoder.
- Timings include process startup and file I/O. On short files such as
  `silence16.wav`, launch overhead dominates the reported throughput.
- Encoding is single-threaded. Multithreading, SIMD and a seek index are
  future work; the decoder is already fast relative to the encoder.
- Results will differ on other CPUs, storage, kernels, compiler versions and
  system load. Re-run the harness to get numbers for your machine.
